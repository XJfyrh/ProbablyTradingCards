# 审查代码注释

1. 从仓库根目录运行 `python scripts/check_comments.py --list`，按请求选取文件。记录审查时的 Git 提交、文件和行号。一段连续注释表达同一理由时可合并审查。输出中的 `directive` 可能影响解释器、构建或许可，保留其功能。Python 的命令行帮助也可能直接读取 `__doc__`。
2. 对每段读到它所解释的分支、真实调用方和能够区分两种行为的测试，再决定去向。

   | 分类 | 判断与处理 |
   | --- | --- |
   | 赘述 | 从紧邻代码或断言就能读出同一件事，删除。 |
   | 过时 | 当前入口、数据格式或测试与描述矛盾，引用现状并删除旧说明。 |
   | 借口 | 注释为绕开约束、手工模拟被测结果或跳过真实入口提供理由。核实会漏掉哪种故障，查重后按任务授权在项目中建 Issue，写清证据和修复的验收条件，再删除注释。 |
   | 决策记录 | 去掉说明会失去外部约束或设计理由。把条件、原因及源码或测试入口写入[实现决策](../../../docs/development/实现决策.md)，已有说明可直接引用，再从源码移除。 |

3. 把逐条分类和依据放在本次审查记录或 PR 内。若分批清理，注明已审范围和待审范围。对只删注释的文件核对语句、指令与测试断言保持原样。运行 `python scripts/check_comments.py --base <审查起点>` 和受影响的检查。

解析依赖与基线选择见[贡献说明](../../../CONTRIBUTING.md#维护代码注释)。本地文件名和行号足以查阅当前改动，给 Issue 或 PR 引用旧注释时应链接到审查起点的提交。
