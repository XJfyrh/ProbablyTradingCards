# 审查代码注释

## 列出审查范围

从仓库根目录运行 `./.venv/Scripts/python.exe scripts/check_comments.py --list`。首次使用先按贡献说明安装依赖。记录审查起点的 Git 提交，并从清单中选出本次涉及的文件。连续几行共同解释一个决定时，按一段审查。[依赖与基线](../../../CONTRIBUTING.md#维护代码注释)

清单中的 `comment` 和 `doc` 都需要读上下文。`directive` 标出解释器、构建或许可所需的指令。另查语言自身的指令和会被程序读取的文字，例如 Python CLI 可能用 `__doc__` 生成帮助。保留这些用途。

## 核实每段注释

找到注释所指的代码、实际调用方或测试断言。判断一项测试能否发现某个错误时，沿真实入口走一遍，或在独立副本中引入该错误并观察断言。先记下依据，再处理注释。

| 分类 | 如何核实与处理 |
| --- | --- |
| 赘述 | 指出哪条语句、名称或断言已经表达同一件事，删除注释。 |
| 过时 | 找到与原说明相冲突的当前入口、数据格式或行为，记录差异并删除注释。 |
| 借口 | 查明被绕过的约束和会漏掉的故障。例如，测试手动移除进货溢价后再断言价格恢复，就测不到柜台成交遗漏清理。搜索已有 Issue，引用同一缺口的记录或按任务授权建单，写明复现证据和修复后应通过的检查，再删除注释。 |
| 决策记录 | 写明什么条件下需要这项设计，以及改动时要满足的外部约束。在[实现决策](../../../docs/development/实现决策.md)补充原因和源码或测试入口，已有专题说明时链接对应章节。确认读者能找到依据后，删除源码中的注释。 |

## 留下证据并验证

在 PR 或审查记录中逐段列出原位置、分类、依据，以及对应的文档或 Issue。引用已提交的注释时，链接到仍含原文的提交和行号。仅存在于工作区的注释，记录文件、改动前行号及足以辨认的原文。分批清理时列出本批处理的范围和剩余范围。

对只删注释的文件，核对可执行代码、机器指令和测试断言。用 `--base` 对照审查起点运行注释检查，再按受影响的代码选择测试。[注释检查命令](../../../CONTRIBUTING.md#维护代码注释) · [测试与试玩](../../../tests/README.md)
